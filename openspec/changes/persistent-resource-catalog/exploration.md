## Current architecture and exact seams

- Pure catalog/domain shapes are in `apps/backend/src/resource-master/domain/types.ts`: `ResourceCatalog` contains one class definition, one family, one type, attribute definitions, option sets/options, natural units, applicability bindings/rules, and presentation ordering; active flags occur on all catalog records. Applicability modes are REQUIRED/OPTIONAL/FORBIDDEN/NOT_APPLICABLE and attribute kinds are CONTROLLED_OPTION/INTEGER/DECIMAL/BOOLEAN/CONTROLLED_TEXT/QUANTITY.
- Pure schema behavior is in `domain/schema.ts`: family bindings inherit, type bindings replace completely, inactive type bindings suppress inheritance, duplicate same-scope bindings fail, and equality-only rules use explicit defaults and reject conflicting matches.
- The current productive Cable literal is `infrastructure/cable-catalog.ts`: MATERIAL → CONDUCTORES → CABLE; five attributes; four option sets; M/ROLLO units; family bindings; DESNUDO makes color and voltage NOT_APPLICABLE; presentation order is explicit.
- `application/resource-master.ts` synchronously closes over a `ResourceCatalog` at construction, while all ten `ResourceMaster` methods are asynchronous because `ResourceRepository` is Promise-based. Catalog consumers are taxonomy, effective schema, options, units, create validation/canonicalization, non-identity update validation/search projection, search summary/projection, and description. Get/deactivate only need catalog today indirectly through the shared master, but describe and search visibly depend on current names/labels/presentation.
- Production composition roots are `infrastructure/convex-resource-master.ts`, which injects `cableCatalog` plus `ConvexResourceRepository`, and `convex/resourceMaster.ts`, which registers four public queries (`getTaxonomy`, `getEffectiveResourceSchema`, `getValidOptions`, `getNaturalUnits`), three public mutations (`createResource`, `updateNonIdentityData`, `deactivateResource`), and three more public queries (`getResource`, `searchResources`, `describeResource`). The internal catalog port must not be exported from `public.ts`/`index.ts`.
- Public contract impact: preserve method signatures where possible, but add a stable explicit catalog-unavailable/uninitialized error code to `public.ts` and its Convex validator; Domain-invalid reconstructed data should remain an explicit integrity failure. Every operation instantiated through the Convex composition root is affected by catalog acquisition, while public method names and payloads need not change.
- Existing Resource persistence is `resources` + `resourceAttributes`. `ConvexResourceRepository.listPage` currently reconstructs attributes per resource (an existing Resource Search N+1); binding scope explicitly excludes changing this. Catalog loading itself must be one bounded aggregate read and must not add per-resource catalog reads.

## Recommended architecture

1. Introduce a pure immutable `ResourceCatalogSnapshot`, with no Convex types/IDs: `{ catalogKey, revision, bootstrapVersion, catalog }`, where `catalog` preserves all current ordered arrays, names, labels, active states, applicability/rules, units, and presentation. Keep business semantics in pure types and add `validateResourceCatalogSnapshot` as the complete trust-boundary validator.
2. Add capability ports under Application: `ResourceCatalogReader { loadSnapshot(): Promise<ResourceCatalogSnapshot> }` for runtime and a separate deployment capability such as `ResourceCatalogSnapshotWriter { replace(candidate, expectedRevision): Promise<...> }`. The writer must not be part of `ResourceMaster`, `public.ts`, or any UI/client contract. Tests use an in-memory reader/writer and a test-only fixture.
3. Change `createResourceMaster` to receive a reader and load/validate one snapshot at the start of each application operation. A Convex query/mutation context gives a transactionally consistent read; mutations then validate against and persist Resource state in the same Convex transaction. Do not cache globally or fall back.
4. Use one aggregate-oriented Convex table, e.g. `resourceCatalogSnapshots`, with one complete bounded snapshot document per `catalogKey`: metadata (`catalogKey`, integer `revision`, `bootstrapVersion`/payload identity) plus embedded catalog content. Index `by_catalog_key`; query with `.withIndex(...).unique()`. Current Cable is tiny relative to Convex document/array limits, so one read is simplest, atomic, consistent, and has zero catalog N+1. A mutation performs expected-revision OCC and replaces the complete aggregate. Nested active flags provide lifecycle; stable codes are validated as immutable for this slice. If durable revision history becomes a requirement later, immutable revision documents plus a head table are viable but unnecessary now.
5. Bootstrap through a dedicated `internalMutation` module only. Convex 1.45.0 is installed and generated server types expose `internalMutation`/`internalQuery`, so client-inaccessible bootstrap is feasible. Trusted deployment tooling may invoke the internal function using deployment credentials; no public mutation, action wrapper, UI hook, or `api.*` route is added. Exact CLI invocation should be verified during implementation against the deployed 1.45 toolchain.
6. Bootstrap protocol: construct migration candidate → pure validation before DB write → load current aggregate by indexed key → same bootstrap identity plus semantic equality returns an idempotent no-op → different content requires `expectedRevision` (0 for absent) and conflicts on mismatch → atomically insert/replace → reconstruct through the normal adapter → validate after read → compare full semantic round trip before reporting success. Equality includes codes, names, labels, active flags, array/order semantics, rules/defaults, units/policies, presentation, and every input used by display/search; it excludes only Convex metadata. No commit-then-confirm-read outside the mutation is needed.
7. Cutover: deploy additive optional table/functions and readers; run internal bootstrap; prove idempotency and full round trip; switch both query and mutation composition roots to Convex reader in one release; verify gates; remove production literal immediately. There is no dual authority, runtime fallback, or fixture/migration read after cutover.

## Artifact separation

- Production: pure snapshot/validation, runtime reader port, Convex adapter/table, and composition wiring.
- Test: `apps/backend/tests/fixtures/cable-catalog.ts` and in-memory catalog port only; architecture rule must reject production imports from test/fixture paths.
- Migration/deployment: a versioned Cable payload and internal bootstrap entrypoint, not imported by normal runtime composition. The initially equivalent payload and fixture remain separate copies/responsibilities, with equivalence asserted by tests rather than shared authority.

## Alternatives rejected

- Normalized multi-table catalog: unnecessary joins/bulk orchestration, larger consistency surface, and greater N+1 risk for a bounded aggregate.
- Embedded snapshot on every Resource: duplication, stale copies, and dual authority.
- Immutable revisions plus head table now: sound but extra documents/indexes/read for no stated history requirement; revisit only if revision history/audit becomes a product requirement.
- Public bootstrap mutation protected only by convention: violates internal-only binding and is unsafe before auth.
- Runtime TypeScript fallback, fixture reuse, dual reads/writes, generic repository/CRUD, or legacy schema port: all conflict with frozen decisions.

## Risks and genuine blockers

No product decision currently blocks proposal/spec/design. Design must explicitly bound the aggregate below Convex document/array limits, choose the stable catalog key and bootstrap version naming, and define deterministic semantic equality; these are design details, not product blockers. Risks are accidental fixture/migration imports, incomplete validation, labels/order omitted from equivalence, internal function accidentally wrapped publicly, stale-code mutation, global snapshot caching across Convex transactions, and scope creep into existing Resource Search hydration. Operationally verify the internal-function deployment command and the frozen-register checksum before implementation authorization.
